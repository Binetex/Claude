## 1. Что это за сервис

Floremart — внутренняя операционная система сети цветочных магазинов в США. Не витрина
и не маркетплейс: сами продажи идут на внешних сайтах (Shopify и WooCommerce), а Floremart
принимает оттуда заказы и ведёт их через всё исполнение — от оплаты до доставленного букета
и расчёта с флористом.

Кого обслуживает (три роли, три разных интерфейса):

| Роль | Что делает | Что видит |
|---|---|---|
| `OWNER` (владелец) | всё: настройки, магазины, интеграции, финансы, автоматизации | всё, включая маржу |
| `FLORIST` | принимает заказы, собирает букеты, отмечает готовность, ведёт свои расходы | только свои заказы и свои деньги |
| `CALL_CENTER` | правит данные заказов, общается с клиентами | заказы без финансов |

Ключевые бизнес-цепочки, которые система закрывает:

1. **Приём заказа.** Webhook или синхронизация из Shopify/WooCommerce → нормализация →
   создание `Order` со снимками товаров, цен, адресов.
2. **Назначение флориста.** Приоритеты по магазину, история назначений, снимок цены флориста
   в момент назначения.
3. **Производство.** Статусы, фото букета, готовность, печать открыток и записок.
4. **Доставка.** Курьеры через Burq: черновик заказа доставки создаётся заранее (draft-first),
   флорист сам отправляет его в работу, статусы приходят вебхуками, фиксируется proof of delivery.
5. **Коммуникации.** SMS и звонки через QUO (ex-OpenPhone), транзакционный email через Brevo,
   служебные уведомления сотрудникам в Telegram. Вся переписка привязывается к заказу.
6. **Автоматизации.** Правила «событие заказа → сообщение» и линейные цепочки шагов с задержками.
7. **Финансы.** Расчёт прибыли по дню, доли основного флориста, фиксированной цены вторичного,
   расходов, комиссий эквайринга, налогов, выплат и бонусов.
8. **Платежи.** Мониторинг Airwallex (BNPL/Klarna) — сверка того, что заказ реально оплачен.

## 2. Стек

**Язык:** TypeScript целиком (strict). JS только в двух конфигах PM2. Никакого второго языка,
никакого Python, никаких скомпилированных частей.

| Слой | Технология | Версия |

| Фреймворк | Next.js (App Router, Server Components, Server Actions) | 16.2.10 |

| Стили | Tailwind CSS | 4 |
| Компоненты | Radix UI (dialog, popover, tooltip, slot), lucide-react, sonner, recharts, react-day-picker | — |
| ORM | Prisma + `@prisma/adapter-pg` | 7.8 |
| БД | PostgreSQL | — |
| Валидация | zod | 4.4 |
| Сессии | jose (JWT в httpOnly-cookie) + bcryptjs | — |

## 4. Как устроено (архитектура)

### 4.1 Два процесса, и всё

```
Nginx ──► floremart        (PM2, Next.js, порт 3010)  ← UI, server actions, webhooks
      └─► floremart-worker (PM2, scripts/outbox-worker.ts) ← вся фоновая работа
                    │
                    └── PostgreSQL (единственное хранилище состояния)
```

Ни Redis, ни RabbitMQ, ни Kafka, ни отдельного cron. Это принятое решение, а не недоделка.

### 4.2 Outbox — сердце всей асинхронности

Единственный механизм отложенной и фоновой работы. Таблица `OutboxEvent`: тип события,
агрегат, JSON-payload, `idempotencyKey` (уникальный — дедуп на уровне БД), статус
(`PENDING/PROCESSING/PROCESSED/FAILED/DEAD_LETTER`), счётчик попыток, `availableAt` для
отложенности, lease-поля для восстановления после падения воркера.

Свойства: durable (не теряется при рестарте), at-least-once, экспоненциальный backoff,
dead-letter с уведомлением владельцу в Telegram. Расписание — это и есть опрос outbox
(`availableAt` в будущем = «запусти в 9:00 по времени магазина»).

Воркер (`scripts/outbox-worker.ts`) — таблица `eventType → handler`, сейчас 14 обработчиков.
**Новая фоновая задача = новая строка в этой таблице.** Второй воркер и вторая очередь не заводятся.

Соседние таблицы: `ProcessedOperation` — guard «это побочное действие уже выполнено»
(чтобы повторная доставка события не отправила второй SMS), `Message`/`OrderCommunication` —
журнал того, что реально ушло.

Есть ещё in-process `EventBus` (`src/events/bus.ts`) — исторический слой, синхронный и
не durable. Реестр типов событий `DomainEventMap` из него используется как контракт, но
реальная доставка идёт через outbox. Это единственное заметное дублирование в архитектуре.

### 4.3 Слои

```
Страница/компонент (RSC или "use client")
        │
Server Action ("use server", 35 файлов) ──► RBAC guard (requireRole / requireOrderEditor)
        │
src/modules/<домен>/  — бизнес-логика, чистые функции + сервисы
        │
Prisma ──► PostgreSQL
        │
src/outbox/ ──► воркер ──► src/integrations/<провайдер>/ ──► внешний мир
```

Обычного REST API у системы **нет**. Наружу открыто всего 7 HTTP-роутов, и все — входящие
вебхуки либо служебные:

| Роут | Назначение |
|---|---|
| `/api/health` | health-check для Nginx/PM2, без авторизации |
| `/api/media/[name]` | отдача загруженных фото |
| `/api/webhooks/[platform]` | Shopify |
| `/api/webhooks/woocommerce/[siteId]` | WooCommerce |
| `/api/webhooks/burq` | статусы доставки |
| `/api/webhooks/quo` | входящие SMS и звонки |
| `/api/integrations/shopify/oauth/callback` | установка приложения |

Всё остальное общение с системой — через 55 страниц дашборда и server actions. Именно поэтому
подключение внешних сервисов требует новой папки роутов: сейчас данные наружу отдавать нечем.

### 4.4 Приём вебхука — единый шаблон

Все четыре вебхука сделаны одинаково, и это важный для понимания паттерн:

1. Проверить подпись (HMAC, per-Site секрет из зашифрованного поля; у Shopify — с окном
   ротации client secret).
2. **Ничего не обрабатывать в запросе.** Положить сырое событие в outbox и вернуть 200.
3. Воркер разбирает событие своим handler'ом, повторяет при сбоях.

Провайдер никогда не получает таймаут из-за нашей медленной логики, и ни одно событие не
теряется из-за ошибки обработки.

### 4.5 Мультитенантность

Всё висит на `Site` — магазин. Один `Site` = один внешний сайт (Shopify или WooCommerce) со
своими credentials, таймзоной, номером телефона QUO, настройками email, правилами
автоматизаций, ставками расходников и налоговой политикой. Заказы, товары, вебхуки — всегда
с `siteId`. Отдельных схем БД или изоляции на уровне соединения нет: разделение логическое.

### 4.6 Безопасность

- Сессии: JWT (HS256, `AUTH_SECRET`) в httpOnly-cookie на 7 дней, пароли — bcrypt.
- Авторизация: guard-функции в `src/lib/rbac.ts`, вызываются в начале каждого server action.
  Нет middleware-перехвата — защита держится на дисциплине «не забыть guard».
- Секреты магазинов (Shopify client secret и токен, Woo ключи, API-ключи QUO/Brevo, подписи
  вебхуков) шифруются AES-256-GCM (`src/lib/crypto/secretBox.ts`) и лежат в БД в зашифрованном
  виде; для UI хранится только маска (`********abcd`). Поддерживается ротация ключа шифрования.
  Легаси-исключение: у старых Shopify-подключений `shopifyAccessToken` лежит открытым текстом.
- 153 файла помечены `import "server-only"` — физическая гарантия, что серверный код
  (и секреты) не попадёт в браузерный бандл.

### Почему финансы — самая сложная часть

Три правила, из которых выведено всё остальное (нарушать нельзя):

1. **Заработок выводится, решения записываются.** Долг флориста нигде не хранится — он
   считается на лету (`balance.ts`). В книгу `LedgerEntry` пишутся только решения владельца:
   выплата, бонус, корректировка. Начислений в книге нет.
2. **День считается целиком или не считается.** Неизвестный расход — это не ноль. Пока по
   любому заказу дня не хватает данных, весь день не даёт заработка, а причина висит в
   очереди «Требует заполнения» (`FinanceIssue`).
3. **Одна настройка — одно значение.** У ставок, комиссий и налоговых политик нет периодов
   действия: строка на область, текущее значение, история правок в `FinanceAudit`. Прошлое
   пересчитывается по текущим цифрам.

`LedgerEntry` — **append-only на уровне БД**: триггер Postgres запрещает UPDATE и DELETE,
поэтому у модели нет даже `updatedAt`. Исправление оформляется новой записью с ссылкой
`reversedEntryId`.

Единственная точка пересчёта после любой правки входных данных — `fix.ts::recalculateAffectedFinance`.
Копий быть не должно: они уже существовали в двух экземплярах, и когда правился один, второй
продолжал считать по-старому. Аналогично `balance.ts` — единственный источник долга;
второй способ посчитать остаток уже приводил к расхождению чисел между экранами.

Устройство: `dayCalc.ts` (чистая формула, без БД) → `dayFinance.ts` (сбор дня, запись
`DayFinance`) → `balance.ts` (долг) → `fix.ts` (пересчёт). Плюс `flowerExpenses.ts` (645 строк —
самый большой файл проекта), `issues.ts`, `orderExpenses.ts`, `settingsAdmin.ts`.

## 6. Модель данных: главные сущности

63 модели, но каркас держится на десятке.

**`Site`** (магазин) — корень мультитенантности. Платформа, credentials (зашифрованы),
таймзона, статусы подключений, настройки Burq/QUO/email/автоматизаций/финансов.

**`Order`** — центральная сущность, ~90 полей. Особенности:
- **Пять независимых статусов** вместо одного: `paymentStatus`, `orderStatus`,
  `assignmentStatus`, `deliveryStatus`, `syncStatus`. Заказ может быть оплачен, назначен,
  но не готов — и это разные оси, а не одна лента.
- Заказчик (billing) и получатель (shipping) — **отдельные наборы полей внутри заказа**.
  Отдельной таблицы клиентов в системе нет; «клиент» выводится по нормализованному телефону/email.
- Финансы заказа лежат раздельными полями (`itemsTotal`, `tax`, `tip`, `discount`,
  `deliveryCustomerCost`, `customerTotal`, `floristTotal`, `deliveryActualCost`,
  `estimatedProfit`) и доступны только владельцу.
- Текстовые поля хранятся **вместе с оригиналами** (`cardMessage`/`originalCardMessage`) —
  ручная правка не теряется при ресинхронизации.
- Три разных «текста от клиента», которые нельзя путать: `cardMessage` (открытка),
  `customerNote` (заметка оператора), `deliveryInstructions` (нативные инструкции доставки Shopify).
- Идемпотентность приёма гарантирована БД: `@@unique([siteId, externalId])`.

**`OrderItem`** — позиция как **снимок**, а не ссылка: название, вариант, SKU, фото, состав,
цена клиента и цена флориста копируются в момент заказа. Снимок должен переживать физическое
исчезновение товара из каталога. `productId`/`variantId` — свободные строки, не FK.

**`Product` / `ProductVariant`** — каталог. Цена флориста и состав букета живут на **варианте**.

**`Florist`**, **`OrderAssignment`** (история назначений), **`FloristPickupLocation`**.

**`OrderCommunication`** — единая история переписки (QUO): SMS, звонки, voicemail. Тип,
направление, роль стороны, статус, время, id провайдера. `orderId` nullable — непривязанные
события живут в разделе «Нераспознанные коммуникации». Идемпотентность по
`(provider, providerEventId)`. Есть и старая модель `Message` — простая, привязана к заказу жёстко.

**`Delivery` / `DeliveryIntent` / `DeliveryStatusEvent`** — доставка. `DeliveryIntent` — план
создать черновик, `Delivery` — конкретная попытка, `DeliveryStatusEvent` — история статусов
с источником изменения.

**`OutboxEvent`**, **`ProcessedOperation`** — очередь и guard идемпотентности.

**`Automation` / `AutomationJob` / `AutomationFlow` / `AutomationFlowRun`** — правила и цепочки.
Правило и цепочка — **разные сущности**, не объединять.

**`LedgerEntry`**, **`DayFinance`**, **`FloristFinanceProfile`**, **`FinanceIssue`**,
**`FinanceAudit`** — финансы.

**`IntegrationSecret`** — зашифрованные ключи провайдеров вне привязки к магазину.

## 7. Автоматизации и события

Внутренний реестр триггеров (`modules/automations/triggers.ts`) — **строковый app-registry,
новый триггер добавляется записью в файл, без миграции БД**:

`ORDER_CREATED`, `ORDER_PAID`, `ORDER_CANCELLED`, `ORDER_DELIVERED`,
`TRACKING_LINK_AVAILABLE`, `DELIVERY_TODAY`, `PAYMENT_PENDING`, и другие.

Важная деталь для любого будущего потребителя событий: **все эти факты уже проходят через одну
воронку** — `publishAutomationTrigger()`, которая кладёт в outbox событие типа
`sms.automation.trigger` с payload `{orderId, siteId, triggerType, occurrenceKey}`.
То есть в БД уже лежит durable-журнал всего жизненного цикла заказов.

Триггеры публикуются строго на **реальном переходе состояния** и только из «живых» путей
приёма. Ресинхронизация и bulk-backfill молчат — иначе backfill истории разослал бы клиентам
тысячи SMS о заказах прошлого года. Есть защита от двойного `ORDER_DELIVERED` из двух
источников (курьер Burq и платформа Shopify) — у них разные `occurrenceKey`, поэтому обычного
дедупа outbox недостаточно и проверка сделана отдельно.

Каналы: один движок `ChannelSender` обслуживает и одиночные правила, и цепочки. Движок решает
«кому и что», канал — «как отправить». Реестр каналов создаётся один раз в воркере.

## 8. Связность и качество кода

Что честно хорошо:

- **Чистое ядро.** Формулы и решения вынесены в функции без БД (`dayCalc.ts`, `eligibility.ts`,
  `matching.ts`, `policy.ts`) — поэтому 130 юнит-тестов бегают без Postgres.
- **Инъекция зависимостей в обработчиках.** Handler'ы outbox принимают зависимости аргументами
  (`buildDeliveryCompletedHandler({messaging, idempotency, resolve})`) и тестируются на
  in-memory репозитории.
- **Идемпотентность продумана системно**, а не заплатками: уникальные индексы в БД,
  `idempotencyKey`, `ProcessedOperation`, `occurrenceKey`.
- **Комментарии объясняют «почему», а не «что»**, и часто фиксируют уже случившийся баг
  («это уже существовало в двух экземплярах, и когда правился один…»). Для передачи проекта
  это ценнее любой внешней документации.
- **Один способ делать каждую вещь.** Одна очередь, один воркер, один движок каналов, одна
  точка пересчёта финансов, один источник долга.

Где связность высокая и это стоит знать:

- **168 файлов импортируют Prisma напрямую** (`from "@/lib/db"`). Слоя репозиториев почти нет —
  он введён только там, где понадобился для тестов (outbox, Burq draft port). Замена ORM или
  подмена БД в тестах для большинства кода невозможна без переписывания.
- **`Order` — божественная сущность.** ~90 полей и 20+ связей; почти любая фича трогает эту
  модель. Пять статусов дают большую матрицу допустимых состояний, и валидность переходов
  живёт в коде (`lib/statuses.ts`), а не в схеме.
- **Защита прав держится на дисциплине.** Нет middleware, который бы гарантировал проверку роли —
  забытый `requireRole` в новом server action открывает данные. На срезе 2026-08-08 дисциплина
  соблюдена: во всех 33 файлах с директивой `"use server"` guard присутствует. Но обеспечивает
  это только внимательность автора, а не механизм.
- **Дублирование механизмов событий:** `src/events/bus.ts` (in-process, синхронный) и
  `src/outbox/` (durable). Реально работает второй; первый оставляет реестр типов и путаницу.
- **`src/generated/` в дереве исходников.** 141 тыс. строк сгенерированного кода лежит внутри
  `src/`, из-за чего любая наивная метрика по проекту врёт в три раза.
- **Ни одного официального SDK.** Шесть интеграций — свои HTTP-клиенты. При изменении API
  провайдера чинить придётся самим, компилятор о поломке не предупредит.
- **UI почти не покрыт тестами.** 126 клиентских компонентов; проверка — глазами.

## 9. Эксплуатация

**Развёртывание:** один VPS, Nginx → Next.js на порту 3010, продакшен —
`/home/claudecode/htdocs/floremart.com`, git-checkout ветки `main`.

**Деплой:** `./deploy.sh` на сервере — `git fetch` + `reset --hard origin/main` → `npm ci` →
`prisma generate` → `migrate deploy` → `build` (с откатом на `.next.previous` при провале) →
`pm2 reload floremart + floremart-worker` → health-check. Старый rsync-деплой отключён.

**Процессы PM2:** `floremart` (Next.js, fork, автоперезапуск при 500 МБ) и `floremart-worker`.

**Node:** в `package.json` заявлено `>=20.9`, фактически проект собирается и тестируется на
**Node 24** — на 16-м vitest и next падают.

**Переменные окружения** (36 штук), по группам:
- ядро: `DATABASE_URL`, `AUTH_SECRET`, `APP_URL`, `NODE_ENV`;
- шифрование: `CREDENTIALS_ENCRYPTION_KEY`, `..._ACTIVE_KEY`, `..._KEYS`, `..._KEY_PREVIOUS`;
- воркер: `OUTBOX_BATCH_SIZE`, `OUTBOX_POLL_MS`, `OUTBOX_STUCK_MS`, `WORKER_ID`;
- провайдеры: `SHOPIFY_CLIENT_SECRET`, `WOO_*`, `BURQ_*`, `QUO_*`, `BREVO_API_KEY`;
- флаги и режимы: `SHOPIFY_ENABLED`, `WOOCOMMERCE_ENABLED`, `QUO_ENABLED`, `BURQ_ENABLED`,
  `EMAIL_ENABLED`, `TELEGRAM_ENABLED`, `BURQ_RUNTIME_ENABLED`, `AIRWALLEX_MONITORING_ENABLED`,
  `FINANCE_ACCRUAL_ENABLED` и даты старта расчётов.

**Двухуровневые выключатели.** У рискованных подсистем два независимых гейта: глобальный
env-флаг и галочка на уровне магазина. Пример: `BURQ_RUNTIME_ENABLED=false` делает полный
no-op всей Burq-логики, и никакая настройка магазина это не обойдёт. Аналогично Airwallex.
Так новые интеграции раскатываются на один магазин и мгновенно глушатся целиком.

**Наблюдаемость:** логи PM2 в `logs/`, страница `/dashboard/system-events`, dead-letter
уведомления владельцу в Telegram, `/api/health`. Внешнего APM, Sentry и метрик нет.

**Тесты:** `npm test` (vitest). Интеграционные требуют живую Postgres и запускаются
последовательно на отдельной throwaway-базе — на общей БД они друг друга затирают.

## 10. Жёсткие правила проекта

Это не «пока так», а принятые владельцем решения. Любой анализ или предложение должны их учитывать.

1. **Один воркер на всё.** Новая асинхронная задача = новый `eventType` в существующем воркере.
   Второй воркер и вторая очередь не заводятся.
2. **Outbox — единственный механизм фоновой и отложенной работы.** Отдельного cron и
   планировщиков нет: опрос outbox и есть расписание.
3. **Возврат денег клиенту запускается только человеком.** Ни автоматики, ни воркера, ни
   скрипта. Требуется роль OWNER, номер заказа и **пароль учётной записи** (проверяется на
   сервере). Повторов при ошибке нет: обрыв даёт исход «неизвестно», а не «ошибка».
4. **Деньги флориста живут только в `LedgerEntry`.** Мутируемого поля «сколько должны» нет и
   заводить нельзя.
5. **Настройка автоматизаций и email — только владелец.**
6. **Маркетинг остаётся в Brevo.** Floremart отвечает только за транзакционные письма по
   событиям заказа. Рассылки, сегменты, кампании — на стороне Brevo. HTML-шаблоны в код не переносятся.
7. **Правила и цепочки автоматизаций — разные сущности.** Не объединять.
8. **AI-функциональность внутрь Floremart не переносится.** Floremart остаётся операционной
   системой бизнеса и источником данных для отдельных внешних сервисов.

## 11. Чего в системе нет

Полезно знать до того, как что-то планировать:

- **Публичного API нет.** 7 роутов, все входящие вебхуки или служебные. Отдать данные наружу
  сейчас нечем — под это нужна новая папка роутов и аутентификация по API-ключу.
- **Нет таблицы клиентов.** Заказчик и получатель — поля внутри заказа. Профиль клиента
  выводится по нормализованному телефону/email.
- **Нет ролевой модели тоньше трёх ролей** и нет прав на уровне отдельного магазина: владелец
  видит все магазины.
- **Нет мультиязычности** — интерфейс и комментарии по-русски, данные клиентов по-английски.
- **Нет мобильного приложения**, только адаптивный веб.
- **Нет очереди, кэша и CDN.** Postgres — единственное состояние.
- **Нет внешнего мониторинга и алертов**, кроме Telegram при dead-letter.
- **Нет CI.** Тесты и typecheck гоняются вручную; деплой не блокируется красными тестами.
