# Implementation Plan: Планирование времени доставки

**Branch**: `001-delivery-time-planning` (работа в `main`) | **Date**: 2026-09-28 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/001-delivery-time-planning/spec.md`

## Summary

Три слоя поверх уже сделанного строгого окна «с — до»:

1. **Модель времени** (`modules/timing/model.ts` + `stats.ts`): длительности этапов из фактических
   доставок Burq за 60 дней — ожидание курьера (с запасом), дорога по расстоянию (с запасом),
   сборка по размеру для каждого флориста (обычная), «разгон» первого букета дня; пересчёт на лету
   с кэшем на 6 часов; стартовые значения замера 28.09.2026 при нехватке данных.
2. **Расписание флориста** (`modules/timing/planner.ts` + `load.ts`): очередь по крайнему сроку
   (правило Джексона — оптимально для максимального опоздания на одном «станке»), плановое время
   готовности и доставки, риск опоздания; проверка «влезет ли заказ до T» вставкой в очередь. Заменяет
   баллы/клетки (`modules/capacity` verdict) — одна правда о загрузке.
3. **Разговор о времени** (`modules/timing/policy.ts` + `assistant/extractTime.ts`): отдельный
   короткий запрос к модели извлекает из сообщения время клиента как данные; код решает ход
   (спросить срок / подтвердить до срока / спросить запасное / подтвердить / человеку) по расписанию;
   модель пишет ответ по решению; проверка ответа не пропускает время раньше разрешённого. Время
   клиента хранится у заказа (`Order.customerTime`, JSON) и видно в карточке и на графике.

## Technical Context

**Language/Version**: TypeScript 5, Node 24
**Primary Dependencies**: Next.js (App Router, server actions), Prisma 7, DeepSeek (`deepseek-reasoner`)
**Storage**: PostgreSQL (одна аддитивная колонка `Order.customerTime Json?`; `Florist.workStartMin` уже есть)
**Testing**: vitest (чистые модули — юнит-тесты на реальных примерах прода), браузер на `floremart_uitest`
**Target Platform**: сервер Linux (PM2: `floremart` + `floremart-worker`), дашборд в браузере
**Project Type**: web-приложение (монорепо Next.js, модули в `src/modules`)
**Performance Goals**: расчёт расписания дня < 50 мс; статистика — раз в 6 часов на процесс (< 2 с)
**Constraints**: клиенту только английский; ни одного обещания раньше расчётного; миграции только добавляют
**Scale/Scope**: 6 магазинов, 2–3 флориста, до ~15 заказов на флориста в день, ~400 доставок за 60 дней

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Принцип | Как соблюдается |
|---|---|
| I. Молчание безопаснее | Сомнение (нет флориста, далёкий адрес, вызванный курьер, посторонний номер) → человек; проверка ответа режет раннее время |
| II. Решает код | Ход разговора и «успеем ли» считает `policy.ts`/`planner.ts`; модель только формулирует; извлечение — данные, решение — код |
| III. Одна правда | Загрузка — только из расписания (клетки убираются); окно — `windowOf`; время клиента — `customerTime` |
| IV. Простота | Без новой таблицы статистики (кэш в памяти); одна JSON-колонка; расписание — простая сортировка |
| V. Проверено | Тесты на примерах прода для модели, расписания, политики, извлечения; бэктест модели на 60 днях; браузер |
| VI. Решения записаны | Константы с комментариями о решении владельца; CLAUDE.md обновляется в каждом этапе |

Нарушений нет. Отступление одно — второй запрос к модели на сообщение о времени (см. research R5):
оправдано принципом II (решение до ответа), ограничено воротами «в сообщении есть время».

**Structure Decision**: новый модуль `modules/timing` — единственное место, которое отвечает «когда»
и «успеем ли». `modules/capacity` теряет баллы и вердикты (их заменяет расписание), остаётся с
разбором просьб клиента и опозданиями. Ассистент и график читают `timing/load.ts`.

## Этапы выкатки

1. **Модель времени (US1)**: model/stats, начало работы флориста в «Флористах», самое раннее время
   день в день от начала работы/«сейчас», «Как считаем время» на графике. Выкатка.
2. **Расписание (US3)**: planner/load, график по расписанию, вердикты ИИ из расписания, клетки убраны.
   Выкатка.
3. **Разговор (US2)**: customerTime, извлечение, политика, решение в промпте, проверка ответа, запись
   окна, показ в карточке. Выкатка.
