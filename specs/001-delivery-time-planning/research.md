# Research: Планирование времени доставки

Все решения опираются на замер по продовым данным 28.09.2026 (414 доставок Burq за ~60 дней).

## R1. Откуда брать длительности этапов

- **Decision**: из событий Burq по каждой доставке: `SCHEDULED` (курьер вызван) → первое `PICKED_UP`
  или `IN_TRANSIT` (забрал) → `deliveredAt` (доставил). Расстояние — по центрам индексов (`zipGeo`)
  от точки забора доставки (`Delivery.pickupLocationId`) до `Order.zip`.
- **Rationale**: отметки есть у ~97% доставок; внешних сервисов и ключей не нужно.
- **Alternatives**: Google Distance Matrix (платно, ключ, внешняя зависимость); оценка Burq в котировке
  (нет у заведённых руками доставок, и не хранится).

## R2. Какие статистики

- **Decision**: курьер — 80-й перцентиль ожидания; дорога — 80-й перцентиль по корзинам расстояния
  (0–3, 3–6, 6–10, 10–15, 15–25, 25+ миль) с линейной интерполяцией между серединами корзин;
  сборка — медиана интервала между вызовами курьеров у флориста в тот же день, отдельно для
  маленьких и больших; «разгон» дня — медиана (первый вызов в дни с 2+ утренними − начало работы −
  сборка маленького), не меньше 0.
- **Rationale**: курьер и дорога — одиночные слагаемые обещания, для них нужен запас (8 из 10).
  Сборка суммируется по очереди: сумма медиан ≈ медиана суммы; сумма 80-х перцентилей давала бы
  вдвое заниженную загрузку.
- **Замер 28.09.2026 (стартовые значения)**: курьер p80 24 мин; дорога p80: 28 / 51 / 63 / 71 / 90 /
  90 мин по корзинам; сборка Настя 47/64, Ольга 43/63, общая 45/64; первый вызов в загруженные дни:
  Настя медиана 12:09, Ольга 12:34.
- **Alternatives**: линейная регрессия по всем точкам (занижает короткие поездки: 20–28 мин на 1–2
  мили — это время на парковку и передачу, а не дорога).

## R3. Когда пересчитывать

- **Decision**: на лету, кэш в памяти процесса на 6 часов; при нехватке данных (< 20 доставок на
  метрику, < 10 интервалов на флориста и размер) — стартовые значения.
- **Rationale**: без новой таблицы и задачи в воркере (принцип IV); 6 часов ≫ «раз в неделю».
- **Alternatives**: таблица снимков + интервальная задача — лишняя сущность без выигрыша.

## R4. Модель расписания

- **Decision**: одна «линия» на флориста (букеты собираются по одному). Задание = заказ дня с
  размером, сроком (время клиента «до», иначе конец окна), дорогой. Порядок — по последнему моменту
  готовности (срок − курьер − дорога), при равенстве — по началу окна. Готовность k-го = старт +
  разгон + Σ сборок 1..k. Доставка = max(готовность + курьер + дорога, начало окна). Риск — доставка
  позже срока больше чем на 20 минут. Букеты уже готовые/в пути/доставленные в очередь не входят.
- **Старт**: сегодня — max(начало работы, «сейчас»); другой день — начало работы, но раньше, если
  иначе ранний заказ не успеть (заказ заранее можно и очень рано — решение владельца), не раньше 6:00.
- **«Успеем ли до T»**: вставить задание со сроком T; «да», если новое задание не в риске и ни одно
  существующее не стало хуже и не ушло в риск.
- **Rationale**: правило Джексона (EDD) минимизирует максимальное опоздание на одном станке — ровно
  вопрос «не сорвать ни одного срока». Простая сортировка, без оптимизаторов.
- **Alternatives**: баллы/клетки (грубо, не знают время); целочисленная оптимизация (избыточна).

## R5. Как ИИ узнаёт время клиента

- **Decision**: отдельный короткий запрос к модели «извлеки время» (строгий JSON: день, с, до,
  «в любое время», «сейчас»), только если в сообщении есть что-то про время (`mentionsTime`).
  Результат проверяется кодом (формат HH:MM, с < до, день не в прошлом). Затем код решает ход, и
  основной запрос получает готовое решение.
- **Rationale**: решение «спросить срок или подтвердить» должно быть известно до ответа (принцип II);
  регулярки по свободной речи клиента — источник ошибок, которые мы чинили 27.09.
- **Alternatives**: один запрос, где модель сама сравнивает время с порогом (решение в промпте —
  нарушение принципа II); извлечение регулярками (хрупко).

## R6. Где хранить время клиента

- **Decision**: `Order.customerTime Json?` — `{ from, until, altFrom, altUntil, day, source, at }`
  (минуты от полуночи; `day` — к какому дню доставки относится). Чистый модуль `customerTime.ts`
  разбирает и сливает (новое сообщение уточняет старое, не стирая то, чего не касалось).
- **Rationale**: одна аддитивная колонка, форма может меняться без миграций; читается только по
  заказу.
- **Alternatives**: пять колонок (больше миграций, выгоды нет); таблица «сообщения о времени»
  (история уже есть в переписке).

## R7. Ходы разговора и проверка ответа

- **Decision**: ходы `NONE`, `ASK_UNTIL`, `CONFIRM_BY(T)`, `ASK_ALT(earliest)`, `CONFIRM_FROM(F)`,
  `CONFIRM_ANYTIME`, `CONFIRM_AT(T)` (другой день), `HUMAN(причина)`. Для каждого — «раньше какого
  часа нельзя соглашаться» для существующей проверки `confirmsEarlyTime`.
- **Запись**: `CONFIRM_BY` — окно заказа до T (начало окна не раньше «может с»); `CONFIRM_FROM` —
  окно с F до 21:00; `CONFIRM_AT` — окно T–T+30; `ASK_*` — только время клиента, окно не трогаем.
- **Rationale**: окно = обещание (одна правда), время клиента — ограничение для расписания.
