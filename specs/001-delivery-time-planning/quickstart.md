# Quickstart: как проверить планирование времени

## Юнит-тесты

```bash
export PATH="$HOME/.nvm/versions/node/v24.18.0/bin:$PATH"
npx vitest run src/modules/timing src/modules/assistant src/modules/capacity src/lib/deliveryWindow.test.ts
```

Ожидается: модель на выборках даёт стартовые значения замера; расписание ставит заказы по срокам и
помечает риск; политика даёт ходы из таблицы сценариев спецификации (US2 1–6).

## Бэктест модели (прод, только чтение)

Скрипт `scripts/timing-backtest.ts` — для доставок за 60 дней сравнивает оценку «курьер + дорога» с
фактом: доля доставок, где ошибка ≤ 15 мин (цель SC-004 ≥ 70%).

## Тестовая база (`floremart_uitest`, порт 3111)

1. `preview_start floremart-uitest`, войти `owner@local.test`.
2. «Флористы»: у Насти «Начинает работу» 10:00, у Ольги 12:00.
3. «График доставки»: блок «Как считаем время» с цифрами; у флориста очередь с плановым временем и
   риском; клеток нет.
4. Карточка заказа: «Клиент: дома с 11:00 до 16:00» после сохранённого времени клиента.

## Разбор сообщений (без отправки)

Юнит-тесты `handler`-оркестрации с подменённой моделью: «ready at 11» → ASK_UNTIL; «until 4» при
свободном расписании → CONFIRM_BY 16:00 и окно «…–16:00»; «until 1» при занятом → ASK_ALT;
«after 5» → CONFIRM_FROM и окно 17:00–21:00; «tomorrow at 9» → CONFIRM_AT и окно 9:00–9:30.
